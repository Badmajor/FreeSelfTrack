# Техническое задание

## Корпоративный трекер задач

### 1. Общая информация

**Рабочее название:** Task Tracker

**Назначение:**
Веб-приложение для управления задачами, проектами и рабочими процессами команд.

Система должна предоставлять единое пространство для:

* создания и ведения задач;
* распределения задач между сотрудниками;
* контроля статусов и сроков;
* работы команд;
* обсуждения задач;
* хранения истории изменений;
* поиска и фильтрации;
* визуального управления задачами через Kanban-доску;
* получения уведомлений.

Система должна поддерживать несколько организаций, проектов и пользователей.

---

Основные сущности системы:

* Организация;

```

# 3. Организации

Организация является верхним уровнем изоляции данных.

## 3.1. Организация содержит

* название;
* уникальный идентификатор;
* пользователей;
* команды;
* проекты;
* настройки.

Пользователь может состоять в одной или нескольких организациях.

Данные одной организации не должны быть доступны пользователям другой организации без явно предоставленного доступа.

# 4. Пользователи

## 4.1. Данные пользователя

* ID;
* имя;
* фамилия;
* email;
* аватар;
* часовой пояс;
* дата регистрации;
* статус аккаунта;
* роль.

## 4.2. Возможности

* создавать задачи;

* получать уведомления.

# 5. Роли и права

Минимально предусмотреть следующие уровни:

### Системный администратор

Может:

* управлять организациями;
* управлять пользователями;
* управлять проектами;
* изменять системные настройки.

### Администратор проекта

Может:

* управлять участниками проекта;
* изменять настройки проекта;
* создавать и изменять статусы;
* изменять порядок статусов;
* настраивать типы задач;
* управлять доступами проекта.

### Участник проекта

Может:

* создавать задачи;
* редактировать доступные задачи;
* изменять статусы;
* назначать исполнителей в рамках разрешений;
* комментировать задачи;
* добавлять наблюдателей.

### Наблюдатель

Имеет доступ к просмотру задачи и получает уведомления в соответствии с настройками.

Система должна предусматривать возможность дальнейшего расширения RBAC.

## 7.1. Поля проекта

Пример:

```

# 8. Настройка статусов проекта

## 8.1. Общий принцип

**Статусы являются настройкой конкретного проекта.**

Не должно существовать обязательного глобального набора статусов, одинакового для всех проектов.

Каждый проект может иметь собственный набор статусов и собственный порядок прохождения задач.

Например:

### Проект DEV

```text
Backlog
    ↓
To Do
    ↓
In Progress
    ↓
Code Review
    ↓
Testing
    ↓
Done
```

### Проект Marketing

```text
Идеи
    ↓
Планирование
    ↓
В работе
    ↓
Согласование
    ↓
Опубликовано
```

Статусы одного проекта не должны влиять на статусы другого проекта.

---

# 9. Статус проекта

## 9.1. Поля

```text
id
project_id
name
key
color
position
is_final
is_archived
created_at
updated_at
```

### Описание

**name** — название статуса.

**key** — технический идентификатор.

**color** — цвет отображения.

**position** — порядок статуса на Kanban-доске.

**is_final** — является ли статус конечным.

**is_archived** — архивирован ли статус.

---

# 10. Управление статусами

Администратор проекта должен иметь возможность:

* создать статус;
* изменить название;
* изменить ключ;
* изменить цвет;
* изменить порядок;
* сделать статус конечным;
* архивировать статус.

При удалении/архивировании статуса система должна определить, что делать с существующими задачами этого статуса.

Минимальный вариант:

```text
Нельзя удалить статус, если существуют связанные задачи.
Необходимо сначала перевести задачи в другой статус.
```

---

# 11. Workflow

На первом этапе workflow является простым.

Задача может быть переведена из одного статуса в другой, если пользователь имеет соответствующее право.

В дальнейшем может быть реализован механизм ограниченных переходов:

```text
Backlog → To Do
To Do → In Progress
In Progress → Code Review
Code Review → Testing
Testing → Done
```

Для MVP сложный workflow engine не требуется.

---

# 12. Kanban-доска

Kanban является одним из основных представлений проекта.

## 12.1. Основной принцип

**Каждый статус проекта отображается отдельной колонкой Kanban.**

Например:

```text
┌──────────┐ ┌──────────┐ ┌──────────────┐ ┌────────┐
│ Backlog  │ │ To Do    │ │ In Progress  │ │ Done   │
├──────────┤ ├──────────┤ ├──────────────┤ ├────────┤
│ DEV-101  │ │ DEV-105  │ │ DEV-102      │ │ DEV-99 │
│ DEV-103  │ │ DEV-107  │ │ DEV-104      │ │        │
└──────────┘ └──────────┘ └──────────────┘ └────────┘
```

---

# 13. Настраиваемые колонки Kanban

Количество и набор колонок **полностью определяется статусами конкретного проекта**.

Если администратор добавляет статус:

```text
Code Review
```

на Kanban автоматически появляется колонка:

```text
Code Review
```

Если статус архивируется, соответствующая колонка перестаёт использоваться для новых задач.

---

# 14. Порядок колонок

Порядок колонок должен настраиваться отдельно для каждого проекта.

Например:

```text
Backlog
To Do
In Progress
Review
Testing
Done
```

Администратор может изменить порядок:

```text
Backlog
To Do
In Progress
Testing
Review
Done
```

Порядок хранится в поле `position`.

---

# 15. Изменение ширины колонок

Пользователь должен иметь возможность изменять ширину колонок Kanban.

Например:

```text
Backlog     220 px
In Progress 350 px
Review      300 px
Done        220 px
```

Настройки ширины должны сохраняться для пользователя.

Минимальная ширина должна быть ограничена, чтобы колонка оставалась пригодной для использования.

---

# 16. Работа с задачами на Kanban

Пользователь должен иметь возможность:

* открыть задачу;
* перетащить задачу между колонками;
* изменить статус drag & drop;
* создать задачу непосредственно в колонке;
* просматривать основные данные задачи.

При перемещении:

```text
In Progress → Review
```

система должна изменить статус задачи.

Одновременно должна быть создана запись в истории:

```text
Статус изменён:
In Progress → Review
```

---

# 17. Карточка задачи Kanban

Карточка должна отображать минимум:

* ключ;
* название;
* тип;
* приоритет;
* исполнителя;
* теги;
* срок;
* дополнительные индикаторы.

Пример:

```text
┌──────────────────────────┐
│ DEV-123                  │
│ Реализовать авторизацию  │
│                          │
│ 👤 Иван                  │
│ 🔴 High                  │
│ #auth #backend           │
│ 📅 01.10.2026            │
└──────────────────────────┘
```

# 18. Задача

Задача является основной рабочей единицей системы.

## 18.1. Поля задачи

```text
id
project_id
number
key
title
description

type_id
status_id
priority_id

author_id
assignee_id

parent_task_id

due_date

created_at
updated_at
completed_at
```

---

# 19. Ключ задачи

Каждая задача получает уникальный ключ внутри проекта.

Например:

```text
DEV-1
DEV-2
DEV-3
```

Где:

```text
DEV — ключ проекта
1   — номер задачи
```

Ключ должен быть уникальным в пределах организации.

После создания задачи её ключ не должен изменяться.

---

# 20. Типы задач

Для MVP предусмотреть:

* Task;
* Bug;
* Feature;
* Epic.

Типы задач должны быть настраиваемыми на уровне проекта в будущем.

---

# 21. Приоритеты

Базовые приоритеты:

```text
Low
Normal
High
Critical
```

Для каждого приоритета:

* название;
* ключ;
* цвет;
* порядок.

Приоритеты могут быть общими или настраиваемыми для проекта.

---

# 22. Описание задачи

Описание должно поддерживать форматирование текста.

Для MVP:

* обычный текст;
* ссылки;
* списки;
* заголовки;
* код.

В дальнейшем:

* Markdown;
* изображения;
* таблицы;
* упоминания пользователей.

---

# 23. Исполнитель

У задачи может быть:

* один автор;
* один основной исполнитель;
* несколько наблюдателей.

Исполнитель выбирается только из пользователей, имеющих доступ к проекту.

---

# 24. Наблюдатели

Пользователь может подписаться на задачу.

Наблюдатель получает уведомления об изменениях.

Пользователь может:

* добавить наблюдателя;
* удалить наблюдателя;
* подписаться на задачу самостоятельно.

---

# 25. Родительские задачи

Задачи могут иметь родительскую задачу.

Пример:

```text
DEV-100 Авторизация

    DEV-101 Backend
    DEV-102 Frontend
    DEV-103 Tests
```

На первом этапе достаточно одного уровня вложенности.

В дальнейшем возможно создание полноценной иерархии:

```text
Epic
 └── Story
      └── Task
           └── Subtask
```

---

# 26. Связи между задачами

Предусмотреть возможность связывать задачи.

Типы связей:

* blocks;
* blocked by;
* relates to;
* duplicates;
* duplicated by.

Например:

```text
DEV-123 blocks DEV-124
```

---

# 27. Теги

Пользователь может добавлять к задаче несколько тегов.

Примеры:

```text
backend
frontend
bug
urgent
payment
```

Теги должны иметь:

* название;
* цвет;
* проект/организацию;
* дату создания.

---

# 28. Дедлайн

Задаче можно установить дату и время окончания.

Система должна определять:

* задача просрочена;
* срок сегодня;
* срок в будущем;
* задача завершена.

Просроченные задачи должны визуально выделяться.

---

# 29. Комментарии

К каждой задаче пользователь может добавить комментарий.

Комментарий содержит:

```text
id
task_id
author_id
text
created_at
updated_at
```

Пользователь может редактировать и удалять собственные комментарии в рамках разрешений.

---

# 30. Вложения

К задаче можно прикреплять файлы.

Для каждого файла:

* имя;
* размер;
* MIME type;
* автор;
* дата загрузки;
* ссылка на объект хранения.

Ограничить:

* максимальный размер файла;
* допустимые типы;
* количество файлов.

Хранение предусмотреть в S3-compatible storage.

---

# 31. История изменений

Для каждой задачи необходимо хранить audit log.

Фиксируются:

* создание;
* изменение названия;
* изменение описания;
* изменение статуса;
* изменение исполнителя;
* изменение приоритета;
* изменение дедлайна;
* добавление/удаление тегов;
* добавление/удаление наблюдателей;
* добавление комментария;
* загрузка файла;
* изменение родительской задачи;
* изменение связей.

Пример:

```text
27.09.2026 14:32

Иван изменил статус:
In Progress → Code Review
```

* ключу;
* названию;
* описанию;
* исполнителю;

```text
DEV-123

# 34. Фильтрация

Фильтры:

* проект;

* автор;
* тип;
* приоритет;

* срок;

# 35. Сохранённые фильтры

Сохранённый фильтр содержит:

* пользователя-владельца;

---

# 36. Дашборд пользователя

После входа пользователь видит:

* мои задачи;
* просроченные задачи;
* задачи на сегодня;
* задачи в работе;
* недавно изменённые задачи;
* уведомления.

---

# 37. Дашборд проекта

Проектный дашборд должен отображать:

* количество задач;

* количество задач по исполнителям;
* количество просроченных задач;
* количество закрытых задач.

В будущем:

* velocity;
* cycle time;
* lead time;
* burndown;
* throughput.

# 42. Основные API-сценарии

```http
POST /api/projects
```

```http

```

## Создание статуса

```http

```

```http

```

```http

```

## Изменение задачи

```http
PATCH /api/tasks/{task_id}
```

## Изменение статуса

```http
PATCH /api/tasks/{task_id}/status
```

## Добавление комментария

```http
POST /api/tasks/{task_id}/comments
```

## История

```http
GET /api/tasks/{task_id}/history
```

---

# 43. Права доступа

Каждый API endpoint должен проверять:

1. аутентифицирован ли пользователь;
2. состоит ли пользователь в организации;
3. имеет ли доступ к проекту;
4. имеет ли необходимое право;
5. имеет ли право изменять конкретную сущность.

Нельзя полагаться только на проверки frontend.

```text

```

# 56. Ключевой архитектурный принцип

Важнейшее требование системы:

> **Проект является владельцем своего workflow.**

То есть:

```text
Project
   │
   ├── Status A
   ├── Status B
   ├── Status C
   └── Status D
```

а не:

```text
Global Statuses
       │
       ├── Project A
       ├── Project B
       └── Project C
```

Это позволит в дальнейшем сделать разные процессы для разработки, маркетинга, продаж, поддержки, производства и других подразделений без изменения ядра системы.

# 8. Настройка статусов проекта

## 8.1. Общий принцип

**Статусы являются настройкой конкретного проекта.**

Не должно существовать обязательного глобального набора статусов, одинакового для всех проектов.

Каждый проект может иметь собственный набор статусов и собственный порядок прохождения задач.

Например:

### Проект DEV

```text
Backlog
    ↓
To Do
    ↓
In Progress
    ↓
Code Review
    ↓
Testing
    ↓
Done
```

### Проект Marketing

```text
Идеи
    ↓
Планирование
    ↓
В работе
    ↓
Согласование
    ↓
Опубликовано
```

Статусы одного проекта не должны влиять на статусы другого проекта.

---

# 9. Статус проекта

## 9.1. Поля

```text
id
project_id
name
key
color
position
is_final
is_archived
created_at
updated_at
```

### Описание

**name** — название статуса.

**key** — технический идентификатор.

**color** — цвет отображения.

**position** — порядок статуса на Kanban-доске.

**is_final** — является ли статус конечным.

**is_archived** — архивирован ли статус.

---

# 10. Управление статусами

Администратор проекта должен иметь возможность:

* создать статус;
* изменить название;
* изменить ключ;
* изменить цвет;
* изменить порядок;
* сделать статус конечным;
* архивировать статус.

При удалении/архивировании статуса система должна определить, что делать с существующими задачами этого статуса.

Минимальный вариант:

```text
Нельзя удалить статус, если существуют связанные задачи.
Необходимо сначала перевести задачи в другой статус.
```

---

# 11. Workflow

На первом этапе workflow является простым.

Задача может быть переведена из одного статуса в другой, если пользователь имеет соответствующее право.

В дальнейшем может быть реализован механизм ограниченных переходов:

```text
Backlog → To Do
To Do → In Progress
In Progress → Code Review
Code Review → Testing
Testing → Done
```

Для MVP сложный workflow engine не требуется.

---

# 12. Kanban-доска

Kanban является одним из основных представлений проекта.

## 12.1. Основной принцип

**Каждый статус проекта отображается отдельной колонкой Kanban.**

Например:

```text
┌──────────┐ ┌──────────┐ ┌──────────────┐ ┌────────┐
│ Backlog  │ │ To Do    │ │ In Progress  │ │ Done   │
├──────────┤ ├──────────┤ ├──────────────┤ ├────────┤
│ DEV-101  │ │ DEV-105  │ │ DEV-102      │ │ DEV-99 │
│ DEV-103  │ │ DEV-107  │ │ DEV-104      │ │        │
└──────────┘ └──────────┘ └──────────────┘ └────────┘
```

---

# 13. Настраиваемые колонки Kanban

Количество и набор колонок **полностью определяется статусами конкретного проекта**.

Если администратор добавляет статус:

```text
Code Review
```

на Kanban автоматически появляется колонка:

```text
Code Review
```

Если статус архивируется, соответствующая колонка перестаёт использоваться для новых задач.

---

# 14. Порядок колонок

Порядок колонок должен настраиваться отдельно для каждого проекта.

Например:

```text
Backlog
To Do
In Progress
Review
Testing
Done
```

Администратор может изменить порядок:

```text
Backlog
To Do
In Progress
Testing
Review
Done
```

Порядок хранится в поле `position`.

---

# 15. Изменение ширины колонок

Пользователь должен иметь возможность изменять ширину колонок Kanban.

Например:

```text
Backlog     220 px
In Progress 350 px
Review      300 px
Done        220 px
```

Настройки ширины должны сохраняться для пользователя.

Минимальная ширина должна быть ограничена, чтобы колонка оставалась пригодной для использования.

---

# 16. Работа с задачами на Kanban

Пользователь должен иметь возможность:

* открыть задачу;
* перетащить задачу между колонками;
* изменить статус drag & drop;
* создать задачу непосредственно в колонке;
* просматривать основные данные задачи.

При перемещении:

```text
In Progress → Review
```

система должна изменить статус задачи.

Одновременно должна быть создана запись в истории:

```text
Статус изменён:
In Progress → Review
```

---

Карточка должна отображать минимум:

* ключ;
* название;
* тип;
* приоритет;
* исполнителя;
* теги;
* срок;
* дополнительные индикаторы.

Пример:

```text
┌──────────────────────────┐

│ Реализовать авторизацию  │
│                          │
│ 👤 Иван                  │

# 25. Родительские задачи

Задачи могут иметь родительскую задачу.

Пример:

```text
DEV-100 Авторизация

    DEV-101 Backend
    DEV-102 Frontend
    DEV-103 Tests
```

На первом этапе достаточно одного уровня вложенности.

В дальнейшем возможно создание полноценной иерархии:

```text
Epic
 └── Story
      └── Task
           └── Subtask
```

# 26. Связи между задачами

Предусмотреть возможность связывать задачи.

Типы связей:

* blocks;
* blocked by;
* relates to;
* duplicates;
* duplicated by.

Например:

```text
DEV-123 blocks DEV-124
```

# 27. Теги

Пользователь может добавлять к задаче несколько тегов.

Примеры:

```text
backend
frontend
bug

payment
```

Теги должны иметь:

* название;
* цвет;
* проект/организацию;
* дату создания.

---

# 28. Дедлайн

Задаче можно установить дату и время окончания.

Система должна определять:

* задача просрочена;
* срок сегодня;
* срок в будущем;
* задача завершена.

Просроченные задачи должны визуально выделяться.

---

# 29. Комментарии

К каждой задаче пользователь может добавить комментарий.

Комментарий содержит:

```text
id

author_id
text
created_at
updated_at
```

Пользователь может редактировать и удалять собственные комментарии в рамках разрешений.

---

# 30. Вложения

К задаче можно прикреплять файлы.

Для каждого файла:

* имя;
* размер;
* MIME type;
* автор;
* дата загрузки;
* ссылка на объект хранения.

Ограничить:

* максимальный размер файла;
* допустимые типы;
* количество файлов.

Хранение предусмотреть в S3-compatible storage.

---

# 31. История изменений

Для каждой задачи необходимо хранить audit log.

Фиксируются:

* создание;
* изменение названия;
* изменение описания;
* изменение статуса;
* изменение исполнителя;
* изменение приоритета;
* изменение дедлайна;
* добавление/удаление тегов;
* добавление/удаление наблюдателей;
* добавление комментария;
* загрузка файла;
* изменение родительской задачи;
* изменение связей.

Пример:

```text
27.09.2026 14:32

Иван изменил статус:
In Progress → Code Review
```

    ↓
Создание проекта
    ↓
Добавление участников
    ↓

    ↓

    ↓

    ↓

    ↓

# 56. Ключевой архитектурный принцип

Важнейшее требование системы:

> **Проект является владельцем своего workflow.**

То есть:

```text
Project
   │
   ├── Status A
   ├── Status B
   ├── Status C
   └── Status D
```

а не:

```text
Global Statuses
       │
       ├── Project A
       ├── Project B
       └── Project C
```

Это позволит в дальнейшем сделать разные процессы для разработки, маркетинга, продаж, поддержки, производства и других подразделений без изменения ядра системы.
